- Send ciphertext + nonce + authTag + metadata
- Fetch encrypted messages
- Derive the correct local key
- Decrypt locally
- Display plaintext only in client memory/UI state
- Clear sensitive runtime key material when chat session ends

==================================================
VERY IMPORTANT CRYPTOGRAPHIC SEPARATION
==================================================

There are THREE separate cryptographic concepts:

1. ARGON2ID
   Purpose:
   Verify that the supplied shared secret is correct.

2. HKDF
   Purpose:
   Derive deterministic cryptographic key material from the shared secret and the conversation's KDF parameters.

3. AES-256-GCM
   Purpose:
   Encrypt and decrypt message content and authenticate ciphertext integrity.

NEVER use the Argon2 verifier itself as the AES key.

NEVER return secretVerifier to the client as an encryption key.

NEVER treat an Argon2 verifier as a substitute for HKDF.

==================================================
IMPORTANT LOW-ENTROPY WARNING
==================================================

The shared secret may be human-memorable.

HKDF is NOT a password-hardening function.

Therefore:

DO NOT claim that:

human word
→ HKDF
→ automatically strong AES key

is equivalent to password-strengthening.

The implementation must clearly document that the shared secret should be sufficiently high-entropy for the cryptographic design.

If the current product requirements insist on a short/common human word, explicitly flag that as a cryptographic limitation rather than silently pretending HKDF solves password guessing.

Do not silently replace the architecture with a different password protocol.

==================================================
PUBLIC KDF PARAMETERS
==================================================

Each friendship/group must have stable KDF parameters.

Expected data:

kdfSalt
kdf.info
keyVersion
cryptoVersion

kdfSalt:

- cryptographically random
- 16 bytes minimum for our protocol
- generated when the friendship/group shared secret is established
- stored as Base64
- NOT regenerated every chat unlock
- NOT generated for every message
- NOT secret
- may be returned to an authenticated participant

secretSalt:

- belongs to Argon2id verification
- separate from kdfSalt
- never substitute secretSalt for kdfSalt

The distinction is mandatory:

secretSalt
→ Argon2id verification

kdfSalt
→ HKDF key derivation

==================================================
KDF SALT LIFECYCLE
==================================================

When shared secret is first established:

if (!friendship.kdfSalt) {
    generate 16 random bytes
    encode as Base64
    persist
}

Do NOT do:

unlock chat
→ generate new kdfSalt

Do NOT do:

every message
→ generate new kdfSalt

The same friendship/group keyVersion must use the same KDF salt until an intentional cryptographic key rotation occurs.

==================================================
HKDF PROTOCOL
==================================================

Implement HKDF using the browser Web Crypto API.

Use:

window.crypto.subtle

Do NOT implement homemade HKDF.
Do NOT manually reproduce HMAC unless absolutely required by browser compatibility.
Prefer native Web Crypto.

Hash:

SHA-256

IKM:

the shared secret provided by the user.

HKDF salt:

the decoded kdfSalt returned by the backend.

HKDF info:

a deterministic protocol context.

Initial protocol value:

SecureNet/chat/v1

For groups use a deterministic group context while maintaining the same protocol format.

Example concept:

SecureNet/chat/v1
SecureNet/group/v1

Do not include the plaintext message in HKDF info.

Do not include the shared secret in HKDF info.

Do not include a randomly generated value that changes between Alice and Bob.

==================================================
SESSION / KEY RELATIONSHIP
==================================================

ChatSession is authorization state.

CryptoKey is cryptographic state.

Do not confuse them.

ChatSession:

"this user is authorized to access this conversation for 10 minutes"

CryptoKey:

"this client can cryptographically decrypt/encrypt this conversation's messages"

When session expires:

- clear CryptoKey
- clear shared secret from volatile state
- mark conversation locked
- prevent encrypt
- prevent decrypt
- show unlock UI

The encrypted messages remain in backend storage.

==================================================
AES-GCM SERVICE
==================================================

Create:

client/src/services/crypto/aesGcm.service.js

Use:

window.crypto.subtle

Algorithm:

AES-GCM

Key length:

256 bits

Nonce/IV:

12 bytes / 96 bits

Generate a NEW random nonce for EVERY message.

Use:

crypto.getRandomValues()

NEVER:

- increment nonce manually
- derive nonce from message ID
- derive nonce from timestamp
- use session counter as nonce
- reset a nonce counter
- reuse a nonce
- reuse one nonce for an entire conversation

The correct concept is:

Conversation Key V1
    │
    ├── Message 1 → random nonce A
    ├── Message 2 → random nonce B
    ├── Message 3 → random nonce C
    └── Message 4 → random nonce D

Same conversation key.

Unique nonce for every AES-GCM encryption.

==================================================
AES-GCM AUTHENTICATION TAG
==================================================

The authentication tag MUST be verified during decryption.

Do not ignore authentication failure.

If ciphertext, nonce, key, or AAD is incorrect:

decrypt operation must fail.

Do NOT return partial plaintext.

Do NOT display decrypted content after authentication failure.

Return a controlled crypto error such as:

{
    success: false,
    error: "Message authentication failed"
}

Do not expose unnecessary cryptographic internals.

==================================================
AAD
==================================================

Use AES-GCM Additional Authenticated Data.

Create deterministic AAD based on non-secret message context.

Use the exact same AAD during encryption and decryption.

Example:

SecureNet|friendship|<friendshipId>|v1|key1

or:

SecureNet|group|<groupId>|v1|key1

The format must be deterministic and documented.

AAD MUST NOT contain:

- plaintext
- shared secret
- AES key

The same message context must produce identical AAD on Alice and Bob clients.

If the AAD differs, decryption must fail.

==================================================
MESSAGE SERVICE
==================================================

Keep:

client/src/services/message.service.js

as the orchestration layer.

Responsibilities:

sendMessage()

sendMessage():

1. Validate friendshipId OR groupId.
2. Determine conversationId.
3. Check active conversation CryptoKey.
4. Reject if locked.
5. Construct AAD.
6. Encrypt locally.
7. Send encrypted payload to backend.
8. Never send plaintext.

getMessages():

1. Validate conversation identifier.
2. Check active conversation session/key.
3. Retrieve encrypted messages.
4. For each message:
    - select correct keyVersion
    - construct AAD
    - decrypt locally
5. Return decrypted data to UI state.
6. Never send plaintext back to backend.

Do not place cryptographic primitives directly in message.service.js.
Call hkdf.service.js / aesGcm.service.js / key.service.js.

==================================================
SESSION EXPIRATION
==================================================

ChatSession expires after 10 minutes.

Client must monitor expiresAt.

At expiration:

1. lock conversation
2. clear CryptoKey from key service
3. clear shared secret from runtime state
4. invalidate local session state
5. prevent new messages
6. prevent decryption
7. show unlock state

Do not delete encrypted messages.

Do not destroy conversation history.

User must unlock again.

==================================================

This is mandatory.

Alice's Bob key:

Every conversation has separate cryptographic context.

Use conversationId as a strict key-cache namespace.

==================================================
NO "SAME KEY + SAME NONCE" ERROR
==================================================

The key may remain the same for multiple messages during keyVersion 1.

The nonce MUST NOT.

Correct:

Key V1 + Nonce A → Message 1
Key V1 + Nonce B → Message 2
Key V1 + Nonce C → Message 3

Incorrect:

Key V1 + Nonce A → Message 1
Key V1 + Nonce A → Message 2

Do not implement a resettable nonce counter.

Use cryptographically secure random 12-byte nonces for each message.
