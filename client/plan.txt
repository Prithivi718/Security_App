==================================================
CORE SECURITY ARCHITECTURE
==================================================

The system has two different security responsibilities.

SERVER:
- Authenticate user with JWT
- Verify whether user belongs to friendship/group
- Verify shared secret using Argon2id
- Create 10-minute ChatSession
- Validate/revoke ChatSession
- Store encrypted messages
- NEVER decrypt messages
- NEVER store plaintext messages
- NEVER store AES encryption keys
- NEVER return plaintext shared secret
- NEVER return secretVerifier as an encryption key

CLIENT:
- User enters shared secret
- Send shared secret to backend only for authentication/unlock
- Backend returns successful unlock + session information
- Keep the shared secret only in client memory while chat is unlocked
- Derive encryption key locally
- Encrypt plaintext locally before sending message
- Send only ciphertext + nonce + authTag + crypto metadata
- Fetch ciphertext from backend
- Derive the same key locally
- Decrypt locally
- Keep decrypted plaintext only in client memory/UI state
- Clear secret/key material when the session expires or is locked

==================================================
VERY IMPORTANT CRYPTOGRAPHIC DISTINCTION
==================================================

Do NOT do this:

sharedSecret
    ↓
send to backend
    ↓
backend returns Argon2 hash
    ↓
use Argon2 hash as AES key

That is NOT the architecture.

Instead:

CLIENT:
sharedSecret
    ↓
HKDF
    ↓
AES-256-GCM encryption key

SERVER:
sharedSecret
    ↓
Argon2id verification
    ↓
true / false
    ↓
10-minute ChatSession

The Argon2 verifier is for authentication/verification only.

The HKDF-derived AES key is for message encryption/decryption only.

==================================================
IMPORTANT KDF REQUIREMENT
==================================================

The implementation must use a conversation-specific public KDF salt.

There must be a distinction between:

secretSalt:
- Argon2id password-verification salt
- server-side verification metadata
- never used as the AES key itself

kdfSalt:
- public conversation/group key-derivation salt
- safe to return to authenticated participants
- used by client HKDF
- must be stable for the current keyVersion

The backend Friendship and Group models should therefore contain:

kdfSalt

If the current backend models/services do not have kdfSalt yet, DO NOT invent a fake value in the frontend.

Instead:
1. clearly identify the missing backend field/API data requirement
2. create the frontend code expecting kdfSalt
3. document the backend change required

Do not use secretSalt as kdfSalt.

==================================================

- Accept:

- Return a CryptoKey suitable for AES-GCM

Use a fixed protocol context such as:

Do not hardcode a random salt inside the client.

==================================================
AES-GCM SERVICE
==================================================

Create:

services/crypto/aesGcm.service.js

Responsibilities:

encryptMessage({
    plaintext,
    cryptoKey,
    associatedData
})

decryptMessage({
    ciphertext,
    nonce,
    authTag,
    cryptoKey,
    associatedData
})

Use AES-256-GCM.

Generate a fresh cryptographically random 12-byte nonce for EVERY encrypted message.

NEVER:
- reuse the same nonce
- increment nonce manually
- use message ID as nonce
- reset a nonce counter every session
- derive nonce from timestamp

Generate the nonce using:

crypto.getRandomValues()

The nonce is not secret and must be sent/stored with the ciphertext.

The authTag is required for AES-GCM integrity verification.

Do not silently ignore authentication failures.

If authentication/decryption fails:
- return an explicit failure
- do not display plaintext
- do not retry indefinitely

==================================================
MESSAGE READING RULE
==================================================

A message is readable only while the corresponding secure chat session is active.

When:

ChatSession expires
OR
ChatSession is revoked
OR
user manually locks chat

then:

- remove conversation CryptoKey from runtime cache
- clear shared secret from runtime session state
- prevent further decrypt operations
- prevent new message encryption
- require unlock again

Existing ciphertext remains in backend storage.
